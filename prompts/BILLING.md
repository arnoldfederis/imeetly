# Billing Implementation Guide — AiMeetly

## Billing Model Recommendation

**Hybrid: Subscription tiers with usage limits.**

This SaaS has fixed infrastructure costs (AI processing, transcription) that
scale per meeting. A pure subscription model leaves revenue unpredictable at scale;
pure usage-based is hard for users to budget. The hybrid model gives users predictable
pricing while protecting against runaway costs:

- **Free**: 5 meetings/mo, 100MB max file — onboarding & evaluation
- **Pro**: 50 meetings/mo, 500MB max file — individual power users
- **Team**: 150 meetings/mo, 1GB max file — teams/orgs

Note: Storage is internal-only (temporary processing). Raw files are deleted after
successful processing. Storage is not a user-facing product feature.

Future extension: usage-based overage billing for Pro/Team via Polar's metered usage API.

## Architecture

### Where billing code lives

| Concern | Location |
|---|---|
| Plan limits & types | `apps/server/src/modules/billing/plans.ts` |
| Billing controller (oRPC) | `apps/server/src/modules/billing/index.ts` |
| Webhook sync service | `apps/server/src/modules/billing/service.ts` |
| Polar plugin config | `apps/server/src/lib/auth-plugins.ts` |
| Polar SDK client | `apps/server/src/lib/polar-client.ts` |
| Subscriptions table | `packages/db/src/schemas/app.ts` |
| Plan enforcement | `apps/server/src/modules/meeting/service.ts` (checkUsageLimit) |
| Frontend plan display | `apps/web/src/routes/(dashboard)/index.tsx` |
| Frontend limit gate | `apps/web/src/routes/(dashboard)/meetings/new.tsx` |

### Database

The `app.subscriptions` table stores one row per user:
- `plan`: "free" | "pro" | "team"
- `status`: "active" | "canceled" | "past_due" | "trialing" | "inactive"
- `providerCustomerId`: Polar customer ID
- `providerSubscriptionId`: Polar subscription ID

Users without a subscription row are treated as free-tier.

## Polar Integration

### Checkout Flow

Polar checkout is configured via Better Auth's `@polar-sh/better-auth` plugin.
Products are defined in `auth-plugins.ts` with slugs like `pro-monthly`, `team-yearly`.

The checkout URL is generated by Better Auth's Polar plugin endpoints:
- `POST /api/auth/polar/checkout` with `{ productId }` or `{ slug }`
- Redirects user to Polar hosted checkout
- On success, redirects to `successUrl` configured in the plugin

### Webhook Flow

Polar sends webhooks to Better Auth's webhook endpoint. The handlers are configured
in `auth-plugins.ts` under the `webhooks()` plugin:

1. **`onOrderPaid`** — Called when a subscription payment succeeds
   - Extract `customer.id`, `subscription.id`, `product.id`
   - Call `BillingService.syncSubscription()` to upsert the subscription row
   - Maps Polar product IDs → plan names via `PRODUCT_TO_PLAN` in billing service

2. **`onCustomerStateChanged`** — Called on subscription state changes (cancel, etc.)
   - Should call `BillingService.syncSubscription()` with updated status

3. **`onPayload`** — Catch-all for logging

### Product ID Mapping

Polar product IDs are mapped to plans in `apps/server/src/modules/billing/service.ts`:
```
pro-monthly  → d93a06d1-5b31-4102-a022-b5de81f4802f → "pro"
pro-yearly   → abb029b2-d36d-4bb3-b2bc-eaea327495a6 → "pro"
```

## Usage Enforcement Strategy

### Server-side (authoritative)

- `MeetingService.checkUsageLimit(userId)` runs before every `create()` call
- Queries the user's subscription plan and counts meetings created this month
- Throws `ORPCError("FORBIDDEN")` with structured data `{ plan, used, limit }` if over limit
- This is the **only** enforcement point — frontend checks are advisory only

### Frontend (advisory)

- `billing.getPlan` returns `usage.limitReached` boolean
- `meetings/new.tsx` queries this and disables the create button + shows upgrade banner
- Dashboard shows remaining meetings count and warning when <= 3 remaining

### Adding new limits

1. Add the limit field to `PlanLimits` interface in `billing/plans.ts`
2. Add values to the `PLAN_LIMITS` constant
3. Add enforcement logic in the relevant service method
4. Expose the limit in the `billing.getPlan` response
5. Add frontend display/gating

## How Web/Server/DB Interact

```
[Web] ──mutation──> [Server oRPC] ──checkUsageLimit──> [DB: subscriptions + meetings]
                         │                                       │
                         │ if over limit                         │
                         └──> ORPCError("FORBIDDEN", {data})     │
                                                                 │
[Web] ──query──> [Server: billing.getPlan] ──> [DB] ──> { plan, limits, usage }
                                                                 │
[Polar] ──webhook──> [Better Auth] ──> [BillingService.syncSubscription] ──> [DB: subscriptions]
```

## Extension Points

### Adding usage-based billing

Polar supports metered usage via their Usage API. To add:
1. Configure `usage()` plugin in auth-plugins.ts (already imported)
2. After each meeting processing completes, report usage via Polar SDK
3. Polar will bill based on reported usage at end of billing period

### Adding team billing

The `organization` plugin is already configured in Better Auth. To add team billing:
1. Resolve plan from organization subscription, not just user subscription
2. Add `organizationId` to the subscriptions table
3. Update `checkUsageLimit` to check org-level usage for team plans

### Storage

Storage is internal-only. Raw uploaded files are deleted after successful processing.
There are no user-facing storage limits, quotas, or billing. The `meeting_files` table
tracks source file metadata for provenance only.
